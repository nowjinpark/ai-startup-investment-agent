# 멀티 에이전트 과제 범위와 설계

## 과제에서 해야 하는 일

기존 RAG의 AI 스타트업 투자 평가를 멀티 에이전트로 확장합니다. 기존 주제·자료를 이어 사용하면서 실행 흐름과 품질 개선을 추가합니다.

[실습 안내](https://actually-war-1ea.notion.site/Multi-Agent-Orchestration-3d57f4c866938020a992fcc97e942ee6)의 본문·펼침 README 샘플·평가표를 기준으로 정리했습니다. 아래는 요구사항을 구현에 연결한 요약이며 원문 복제본이 아닙니다. 샘플은 정답 코드가 아니므로 조별 선택과 변경 이유를 설명해야 합니다.

| 요구사항 | 이번 선택 |
|---|---|
| Supervisor 또는 Orchestrator-Workers | 독립 조사를 먼저 나눌 수 있어 Orchestrator-Workers 선택 |
| 고정 순서와 다른 동적 동작 | LLM이 작업·질의·완료 조건을 계획하고 Send로 실행 |
| 기술 성숙도·시장성·이해관계자·도메인 적용성 | 모든 기업에 네 관점을 필수로 검사 |
| 명시적인 State 설계 | TypedDict State, 작업별 구조화 출력, 결과 reducer |
| 보고서 품질 평가와 미달 시 재처리 | 근거성·중립성·편향·충실성 판정 후 재조사 또는 재작성 |
| 실행 추적 | LangSmith와 동일 실행의 로컬 결과 연결 |
| 제출 결과 | GitHub·README, 실제 LangSmith 이미지, 최대 10장 평가 보고서 |

## 원문 확인 범위

과제 페이지의 본문뿐 아니라 **접힌 State 설계 항목·README 샘플·평가표**를 펼쳐 확인했고, 연결된 기존 RAG 과제 페이지도 확인했습니다. State의 일곱 기준과 샘플의 작은 항목까지 구현·문서 위치에 대응했습니다.

교재는 **171쪽 전체의 추출 텍스트를 읽었고**, 코드와 도식이 포함된 주요 **13쪽(77·108·113–116·134–137·147–148·150쪽)**은 이미지로도 확인했습니다. 아래 교재 적용표는 그중 이번 과제에 직접 사용한 부분입니다. 모든 페이지를 이미지로 검사했다는 뜻은 아닙니다. 기존 데이터 분석 미니프로젝트에서는 쉬운 한국어 설명·평가 중심 구성·재현 기록 방식을, RAG 프로젝트에서는 원문·검색 코드·팀 역할과 당시 한계를 이어받았습니다.

## 이어 사용하는 것과 바꾼 것

기존 코퍼스는 2026-09-30 수집한 164쪽·15개 후보입니다. BGE-M3 임베딩, FAISS 검색, 기업별 출처 ID와 원문을 재사용합니다. 기존 최종 검토 후보였던 로보아르테·로보콘·리옵스·비욘드허니컴·엔닷라이트를 기본 입력으로 사용합니다.

기존 흐름은 기업마다 기술·시장 분석을 실행하고 투자 판단 후 다음 기업으로 이동했습니다. 이번에는 일을 계획하는 Orchestrator, 작업별 Worker, 결과를 모으는 Synthesizer, 보고서를 검사하는 Evaluator와 Gate를 나눴습니다. 기존 18점 투자 평가표는 교수님의 100점 과제 평가표와 다릅니다.

기존 자료를 재사용하는 것은 최신 정보를 새로 수집했다는 뜻이 아닙니다. 현재 비상장·투자단계·Exit 여부가 미확인이면 그대로 표시합니다. 검색은 기존 15문항을 이번 환경에서 다시 실행해 [새 결과](../submission/retrieval-evaluation.json)를 남겼습니다. 과거 테스트 개수나 기업 평가를 새 실행의 성과로 보고하지 않습니다.

## 목표와 완료 기준

목표는 검토자가 기업별 근거와 한계를 비교할 수 있는 보고서입니다. 기업 점수를 높게 만들거나 미확인 수치를 채우는 것이 성공 기준은 아닙니다.

1. 기업별 네 관점과 장점·위험·미확인을 포함합니다.
2. 주장에 원문 출처를 연결하고, 회사·고객·투자자·산업 통계를 혼동하지 않습니다.
3. 입력에 따라 계획 또는 실행 경로가 달라지는 과정을 실제 기록으로 보여줍니다.
4. 품질 미달이면 원인에 맞는 부분을 다시 처리하고 정해진 한도 안에서 종료합니다.
5. 입력·환경·모델·자료 시점·명령·결과를 보관해 다른 사람이 확인할 수 있게 합니다.

## 역할과 제어의 경계

- **LLM 판단:** 조사 질문과 검색어, 근거 해석·관점 적합성, 보고서에 사용할 검수된 근거와 확인 조건 선택, 품질 항목별 판정 이유.
- **코드 검사:** 기업·작업 ID·응답 형식·필수 관점·출처 ID, 허용한 근거 선택·원문 문장과 조건의 조립, 결과 병합, 실행 한도, 다음 경로.
- **검토자 결정:** 실제 투자 여부, 최신 기업 상태, 미확인 자격과 실사업 성과의 추가 확인.

평가자는 네 품질 기준의 통과 여부와 이유, 권장 동작, 재조사할 작업 ID를 반환합니다. Gate는 평가와 상태를 읽는 순수 함수입니다. 평가 문장에 명령이 있다고 그대로 새 도구를 실행하지 않습니다.

| 경로 | 조건 | 다시 실행할 부분 |
|---|---|---|
| approve | 필수 검사와 네 품질 기준 통과 | 결과 저장 후 종료 |
| research | 근거 부족 또는 조사 실패 | 지정 Worker·실패 Worker 재실행 |
| rewrite | 자료는 있으나 표현·중립성·구성 문제 | Synthesizer부터 재실행 |
| fallback | 한도·오류·미해결 부족 | 미달 사유와 남은 정보 저장 후 종료 |

유효한 재조사 ID가 없는 research는 기존 계획 전체를 다시 조사합니다. 실패한 Worker는 즉시 한 번 재시도하고 실패 상태를 남깁니다. 이는 보고서 품질 평가 뒤 수정 회차와 구분합니다.

## State 설계

실제 필드는 [state.py](../orchestration/state.py)에 정의합니다. Worker에는 개별 Task·revision·feedback·trace_id를 전달합니다. 전역 상태 전체와 원문 전체를 모든 역할에 넘기지 않습니다.

| 설계 기준 | 반영 방법 | 확인할 것 |
|---|---|---|
| 제어 vs 페이로드 분리 | 입력·계획·결과·보고서와 회차·경로·상태를 분리 | Worker가 제어값을 덮어쓰지 않는지 |
| 관측성 위치 | trace_id·순차 node_status·last_error, Worker 결과 상태·외부 로그 | 실패 작업·입력·회차를 추적하는지 |
| 지속성 비용 | 원문 파일, 출처 ID·필요한 요약만 공유 | 원문이 요약으로 덮어써지지 않는지 |
| 상관 | trace_id·task_id·revision | 기업·작업·회차가 섞이지 않는지 |
| 재개·복구 | SQLite checkpoint, 자료 해시 확인, 사용 비용 복원 | 재시작·재개 후 중복 결과가 없는지 |
| 동시 처리 | 동시 실행 3개, task_id/revision reducer | 완료 순서와 무관하게 같은 결과를 쓰는지 |
| 종료 보장 | 기본 수정 2회, 제어 16단계, recursion 60, 비용 한도 | 자료 부족·API 실패도 종료하는지 |

`merge_results`는 높은 revision을 선택하고 작업 ID로 정렬합니다. 같은 작업·회차의 서로 다른 결과는 조용히 덮어쓰지 않고 오류로 처리합니다. 이전 회차와 자세한 기록은 외부 파일에 두고 State에는 현재 사용할 결과를 둡니다.

## 인용 정확성과 의미 정확성

원문에 인용 문자열이 있는지를 검사하는 것과, 그 인용이 보고서의 주장을 뒷받침하는지를 검사하는 것은 다릅니다. 예를 들어 회사가 발표한 성능 수치를 정확하게 인용했더라도 독립적으로 검증된 운영 효과로 표현하면 의미가 달라집니다. 다른 회사의 성과·고객과 투자자·계획과 완료 실적도 구분해야 합니다.

v3에서는 보고서 평가가 이런 구분을 문제 삼아 재작성과 두 작업 재조사로 이어졌습니다. 재조사 뒤에도 평가가 통과하지 않아 코드의 한도에 따라 fallback으로 끝났습니다. Judge의 판단은 품질 검사 의견이며 모든 지적이 참이라는 독립적인 사실 검증 결과와 동일하지 않습니다.

최종 구현은 Worker의 주장과 연결된 원문을 함께 읽는 **의미 검수**를 추가했습니다. 출처 URL과 회사 홈페이지를 함께 전달하고, 주체·시점·완료 여부·발표와 독립 검증의 차이를 살핍니다. 검수 결과에는 주장이 들어갈 수 있는 관점(`suitable_views`)도 저장합니다. 인용이 실제 존재한다는 사실만으로 시장성·이해관계자 근거로 사용하지 않습니다.

보고서 모델은 검수된 근거 ID와 `condition_codes`를 선택합니다. 코드는 회사와 관점에 맞는 근거만 가져와 문장·출처·추가 확인 조건을 조립합니다. 피드백을 받으면 선택할 근거와 조건을 바꾸며, 출처 번호가 있다는 이유로 새 사실을 덧붙이지 않습니다. 필수 관점의 검수된 근거가 비면 같은 원문에서 짧은 사실을 한 번 다시 확인하고 최초 검수와 복구를 함께 보존합니다. 작성 모델이 관점을 빠뜨려도 허용된 근거 ID가 있을 때만 선택을 보완하고 원래 응답과 보완 기록을 남깁니다. 원문 문자열 검사, Worker 주장 검수, 보고서 품질 평가를 서로 다른 단계로 둡니다.

호출 모델은 `gpt-4.1-mini`와 `gpt-4.1` 별칭입니다. 호출별 단계·모델·토큰은 `llm_usage.json`에 저장했습니다. 응답의 날짜별 모델 스냅샷을 별도로 확보했다고 주장하지 않습니다. temperature 0이어도 새 호출의 계획·표현·시간은 달라질 수 있으므로, 보존된 실행 확인과 같은 결과를 다시 계산한다는 보장은 구분합니다.

단위·통합 검사는 잘못된 기업·인용 거절, 관점 부적합 근거 배제, 병렬 결과의 순서 독립·중복·충돌 처리, 필요한 작업만 재실행, 재작성에서 조사 생략, SQLite 재개, 실패·한도 종료를 포함합니다. 테스트의 가짜 모델 결과를 실제 모델 성능으로 보고하지 않습니다. 실제 API 호출과 LangSmith 기록은 별도로 보존합니다.

승인 판정만으로 내용의 충실도나 사실성이 완전히 보장되지는 않습니다. 시장성은 실제 고객·수요·판매·사업 조건에 답하는지, 이해관계자는 구체적인 사람·조직과 역할이 있는지, 요약은 기업별 확인 결과를 전달하는지도 함께 검토합니다. 기업 자료의 홍보 편향과 노후화, 최신 자격·유료 계약·독립 성능의 미확인 상태는 최종 결과에도 남깁니다.
