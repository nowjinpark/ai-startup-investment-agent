# AI 스타트업 투자평가 — 5인 병렬 개발 및 발표 계획

이 문서는 기업을 교체할 수 있는 AI 스타트업 투자평가 과제를 위한 **협업 시작 계획**이다. 현재 데모는 두 가상 후보를 사용하며, 실제 기업 분석과 담당자 선택·구현·검증은 아직 완료되지 않았다. 팀원은 **김민정, 김희윤, 박종찬, 박진원, 이현우**이며, 이름 순서는 역할 배정이나 기여 순위를 뜻하지 않는다. 캠퍼스·반은 확인 후 기입한다.

## 역할 선택표

각 팀원은 A~E 중 한 역할을 선택한다. PM/PL만 맡는 사람을 두지 않고, 모두 코드와 검증 결과를 남긴다. README는 각자 자신의 파트를 작성한다.

| 역할 | 담당자 | 직접 구현할 일 | 넘겨줄 결과와 검증 |
| --- | --- | --- | --- |
| **A — 자료 전처리·기업 기초** | 미정 | 자료 목록·페이지 수 관리, 문서 정제·분할, 기업 개요·사업 아이디어·창업팀 분석 | 출처가 추적되는 입력 문서와 기업 기초 분석. 추출 누락·중복·페이지 연결 확인 |
| **B — 임베딩 검색·기술 분석** | 미정 | 오픈 임베딩 모델과 검색 저장소, 검색·재검색 도구, AI 기술·제품 분석 | A의 자료를 검색하는 RAG와 근거 문맥. 고정 질문으로 관련 문서 검색 여부 확인 |
| **C — 시장·경쟁 분석** | 미정 | 시장 규모·고객 문제·경쟁 대안 분석 도구 및 에이전트 | 기준일·시장 범위가 명시된 분석. 시장·경쟁·규제 리스크와 인용 검증 |
| **D — 투자평가·판단** | 미정 | Traction·Deal 평가, 점수 집계, 근거 검증, 판단·보류·재검색 요청, 보고서 내용 템플릿 | 근거와 연결된 평가표, 판단 이유, 미확인 정보, 보고서 본문. 합산·근거 누락·보류 조건 검증 |
| **E — StateGraph·PDF 보고서 통합** | 미정 | LangGraph 노드 연결, 상태 전달, 조건 분기·종료, D의 본문을 보고서 파일로 출력 | 전체 실행 경로와 PDF. 정상·근거 부족·후보 소진 경로, 실제 페이지 수와 재현 실행 확인 |

E에게 보고서 내용 작성까지 몰리지 않도록 **D가 점수와 본문 내용, E가 연결과 파일 출력**을 맡는다. A~D도 자기 모듈의 연결 오류를 직접 수정한다. 전체 실행 문제를 E 혼자 해결하는 방식으로 운영하지 않는다.

## 개발 시작 전 함께 확정할 일

- [ ] 각 팀원이 A~E 담당을 선택하고 위 표에 이름을 채운다.
- [ ] 과제가 허용한 5개 도메인 중 하나를 고르고, 분석 대상·기준일·후보 목록을 `config/project.json`에 설정한다. 고객·제품과 결론의 범위도 함께 정한다.
- [ ] `contracts/schema.py`를 읽고 공통 입출력과 상태를 고정한다. 상세 필드를 각 모듈이 따로 만들지 않는다.
- [ ] 투자평가 가중치·점수 척도·판단 기준과 근거 부족 시 최대 1회 재검색 원칙을 합의하고 `config/evaluation.json`에 반영한다. 대상 변경 시 평가 기준도 검토한다.
- [ ] 문서 출처 기록 방법, 200쪽 계산 방식, 공개 저장소에 올릴 수 있는 자료의 기준을 정한다. 모든 후보와 재실행·재검색의 추가 자료를 전체 목록에서 누적 관리한다.
- [ ] Python·라이브러리·임베딩 모델의 버전과 각자의 실행 환경을 맞춘다.
- [ ] 합의한 계약을 따르는 공통 예제 입력과 기대 결과를 준비하고 버전을 고정한다.
- [ ] 모의 결과와 실제 검색·모델 실행 결과를 구분해 표시한다.
- [ ] 공통 파일을 수정할 때 팀에 먼저 알리고, 스키마 변경 시 예제 입력과 관련 모듈을 함께 수정한다.

자료 조사는 각자가 담당하는 분석 분야에서 병렬로 수행한다. A는 모든 자료를 혼자 찾는 대신 중복 제거, 출처·페이지 정리, 전처리 형식 일치를 책임진다. 비밀키와 재배포 권한이 없는 문서 원문은 공개 저장소에 포함하지 않는다.

대상 기업을 바꾸면 `config/project.json`과 자료 목록을 먼저 갱신하고 관련 예제 입력을 교체한다. 회사명·기준일·후보 목록을 프롬프트나 분석 코드에 각각 고정하지 않는다. 설정을 바꿀 수 있다는 사실과 실제 기업 분석이 구현됐다는 사실은 구분한다.

## 기다리지 않고 개발하는 방법

| 역할 | 다른 사람의 완성을 기다리기 전 | 첫 통합에서 바꿔 끼울 것 |
| --- | --- | --- |
| A | 작은 공개 샘플로 추출·정제·기업 분석 작성 | 최종 출처 목록과 실제 문서 |
| B | 계약에 맞는 예제 문서로 임베딩·검색 작성 | A가 만든 정제 문서 |
| C | 예제 검색 결과로 분석과 출처 연결 작성 | B의 실제 검색 함수 |
| D | 예제 분석 결과로 집계·판단·본문 템플릿 작성 | A·B·C의 실제 분석 결과 |
| E | 모의 노드로 그래프·분기·파일 출력 연결 | A~D의 실제 노드·함수 |

**개발의 병렬 작업과 시스템 실행 순서는 다르다.** 다섯 명은 예제 입력으로 동시에 개발하지만, 실제 실행에서는 기업 기초 → 기술 → 시장·경쟁 → 투자 판단 → 보고서 순서로 상태를 전달한다. 실행 노드 수가 팀원 수와 같아야 하는 것은 아니다.

## 1.5일 작업 순서

시각이 명시된 DAY3 제출 마감을 우선한다. 아래 단계 길이는 팀의 실제 시작 시각에 맞춰 배치한다.

1. **착수 합의:** 역할·평가 기준·계약·버전·예제 입력을 먼저 확정한다. E는 즉시 모의 노드를 연결하고 나머지는 담당 모듈을 시작한다.
2. **첫 병렬 구현:** 각자 최소 동작을 만든다. 완성된 함수는 실제 반환 형식과 짧은 검증 결과를 공유한다.
3. **중간 통합:** 전체 로직이 미완성이어도 최소 한 번 처음부터 끝까지 연결한다. 문서 누락·계약 불일치·종료조건을 이때 수정한다.
4. **DAY3 10:00 전:** 설계와 구현 계획의 차이를 정리하고 설계 PDF를 제출한다. 미완성 기능을 완성 기능으로 쓰지 않는다.
5. **오전 통합·실데이터 실행:** 모의 노드를 실제 구현으로 교체하고 정상 경로와 근거 부족 경로를 검증한다. 보고서 본문과 인용을 담당별로 확인한다.
6. **DAY3 15:00 전:** PDF 5쪽 제한·README 재현 절차·공개 파일을 점검하고 개발 결과를 제출한다. 마지막에는 기능 추가를 멈추고 실행 확인과 발표 연습에 집중한다.

## 공동 완료 조건

- [ ] A의 자료를 B가 실제로 검색하고, 검색된 출처가 C·D·보고서까지 유지된다.
- [ ] 근거 부족 → 재검색 1회 → 재판단 또는 보류 경로가 실행 기록으로 확인된다.
- [ ] 첫 후보가 보류되면 다른 후보를 분석하는 분기를 실제 입력으로 검증했다. 가상 후보 데모는 연결 점검으로만 표시한다.
- [ ] 다음 후보가 없거나 모든 후보가 보류인 경우에도 한계가 적힌 보고서로 종료한다.
- [ ] 각자 자신의 분석 주장·숫자·인용을 검토하고 다른 한 명이 교차 확인했다.
- [ ] E 이외의 팀원 한 명이 README만 보고 새 환경에서 실행했다.
- [ ] 각자의 코드 변경과 검증, README 기여를 기록했다. contributor에는 PM/PL 대신 구체적인 작업을 쓴다.
- [ ] 미완료 항목·외부 서비스 의존·모의 데이터 사용 여부를 README에 남겼다.

9분 30초 분량으로 준비하고 30초는 화면 전환·지연에 남겨둔다. 역할 담당자가 정해지면 같은 순서로 발표자를 채운다.
