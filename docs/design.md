# 설계 초안 — 팀이 함께 채우기

**제출용 완성본이 아닙니다.** 팀이 결정한 내용과 실제 구현에 맞춰 수정한 뒤 PDF로 내보냅니다.
기본 흐름은 교수님 과제 안내, 구현 방식은 수업 예제를 참고합니다.

## 1. 분석 대상

- 분야: 미정
- 회사 후보: 미정 (`project.json`에 기록)
- 자료 기준일: 미정
- 해결할 문제: 공개자료를 근거로 스타트업의 기술·시장·경쟁력을 평가한다.
- 결과: 투자 또는 보류 판단, 판단 근거와 한계가 담긴 보고서.

## 2. 역할과 사용할 도구

| 역할 | 입력 | 결과 | 구현 계획 |
|---|---|---|---|
| 기업 탐색 | 후보와 자료 목록 | 기업 개요·팀·실적·출처 | 문서 읽기, 필요하면 웹 검색 |
| 기술 요약 | 회사와 기술 질문 | 핵심 기술·장단점·근거 | **RAG 적용**, 검색 도구와 관련성 확인 |
| 시장 평가 | 회사와 시장 자료 | 수요·시장 규모·위험 | 근거를 넣은 질문으로 LLM 분석 |
| 경쟁사 비교 | 기술·시장 분석과 경쟁 자료 | 차이점과 근거 | 자료 검색·비교 |
| 투자 판단 | 앞 단계 분석 | 항목별 평가·투자/보류 | 합의한 기준과 근거 검사 |
| 보고서 생성 | 판단까지 모인 결과 | 보고서 PDF | 본문 작성 후 파일 저장 |

현재는 각 단계가 가상 예제 결과를 읽습니다. 실제 검색·LLM을 연결한 뒤 완료로 표시합니다.

## 3. RAG 계획

1. PDF를 읽고 출처·페이지 정보를 남긴다.
2. 문서를 작은 조각으로 나눈다.
3. 오픈소스 임베딩으로 바꾸고 검색 저장소에 넣는다.
4. 기술 분석 에이전트가 검색 도구를 호출한다.
5. 찾은 내용이 질문과 관련 있는지 확인한다.
6. 부족하면 질문을 고쳐 최대 1회 더 검색한다. 여전히 부족하면 미확인으로 남긴다.
7. 근거를 넣어 기술 요약을 만들고, 사용한 출처를 전달한다.

재검색 최대 1회는 시간·비용을 제한하기 위한 **팀 초안**입니다.
기본 검색 저장소는 수업 FAISS 예제부터 시작할 계획입니다.
대상이 바뀌면 문서와 검색 저장소도 새로 구성하거나 회사 ID로 검색 대상을 제한합니다.

- 수집 자료와 총 페이지 수: 미정, 전체 200쪽 이하
- 임베딩 후보와 선택 이유: 미정
- 비교할 검색 질문·정답 근거: 미정
- Hit Rate@K·MRR 결과: 미측정
- 문서에 없는 질문·다른 회사의 자료가 섞이는 경우도 확인

## 4. 평가 기준

`evaluation.json`을 함께 수정합니다. 참고 비중은 팀 30·시장 25·기술 15·경쟁우위 10·실적 10·투자조건 10입니다.
각 항목에 대해 **0~5점의 의미와 필요한 근거**를 팀이 정해야 합니다.
70점은 시작 코드의 임시 기준입니다. 자료가 없으면 0점으로 단정하지 않고 미확인으로 둡니다.

## 5. State — 함께 주고받는 정보

`agents/state.py`와 실제로 일치하도록 수정합니다.

| 정보 | 용도 |
|---|---|
| candidates / candidate_index | 후보 목록 / 지금 볼 후보 번호 |
| current_candidate | 지금 분석하는 회사 |
| analyses | 현재 회사의 기초·기술·시장·경쟁 분석과 출처 |
| evaluations | 지금까지 평가한 회사들의 결과 |
| latest_decision | 마지막 투자/보류 판단 |
| mode | 현재는 연결 연습용 demo만 가능 |
| report_paths | 저장된 결과 파일 위치 |

현재 회사의 분석은 새 후보에서 비우고, 끝난 평가 결과는 누적합니다.
실제 Agentic RAG를 붙일 때 질문·검색 결과·메시지·재검색 횟수도 설계에 추가합니다.

## 6. 순서와 종료

README의 흐름도가 현재 6단계 연결 연습입니다.
실제 개발에서는 기술 요약 안에 검색 도구·관련성 확인·제한된 재검색을 붙입니다.
보류이면 다음 후보로 이동하고, 투자 판단이 나오거나 후보를 다 보면 보고서로 끝냅니다.
